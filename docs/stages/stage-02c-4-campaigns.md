## Backend contracts

### Campaign Plan

- `POST /api/campaigns`
- `GET /api/campaigns`
- `GET /api/campaigns/{campaignUuid}`
- `PATCH /api/campaigns/{campaignUuid}`
- `DELETE /api/campaigns/{campaignUuid}`
- `POST /api/campaigns/{campaignUuid}/restore`

Validation:

- `campaignName` is required, trimmed, and at most 256 characters.
- Optional text fields are trimmed; blank becomes `null`; lengths must match V4.
- `startDate`／`endDate` use ISO `YYYY-MM-DD`; when both exist, `endDate >= startDate`.
- Budgets use decimal values with scale at most four and must be non-negative.
- A three-letter uppercase ISO currency code is required when either budget is present.
- `landingPage`, when present, must be an absolute HTTP or HTTPS URL and at most 2048 characters.
- Collection sort allowlist：`updatedAt`, `createdAt`, `campaignName`, `startDate`, `endDate`; always append `campaignUuid` as deterministic secondary ordering.

### Campaign Product association

- `POST /api/campaigns/{campaignUuid}/products`
- `GET /api/campaigns/{campaignUuid}/products`
- `GET /api/campaigns/{campaignUuid}/products/{productUuid}`
- `PATCH /api/campaigns/{campaignUuid}/products/{productUuid}`
- `DELETE /api/campaigns/{campaignUuid}/products/{productUuid}`
- `POST /api/campaigns/{campaignUuid}/products/{productUuid}/restore`

Validation and identity:

- `campaignProductUuid` is generated by the Application; Campaign and Product UUIDs are immutable.
- `priority` is optional and must be at least zero.
- `budgetWeight` is optional, uses scale at most two, and must be between `0.00` and `100.00` inclusive.
- Only one association row may exist for a Campaign／Product pair. Duplicate POST returns `409 RELATIONSHIP_CONFLICT`; an archived duplicate must be restored through the restore endpoint rather than recreated.
- Association list sort allowlist：`updatedAt`, `createdAt`, `priority`, `budgetWeight`; always append `campaignProductUuid`.
- Ownership/path mismatch returns `404 CAMPAIGN_PRODUCT_NOT_FOUND` without disclosing another relationship.

### Common lifecycle and concurrency

- Create returns `201 Created`, `Location`, body, and `ETag: W/"0"`.
- Single read and successful patch／restore return the resource ETag; archive returns `204` plus ETag.
- Patch consumes only `application/merge-patch+json`; missing fields remain unchanged, explicit `null` clears optional fields, unknown or immutable fields fail with `INVALID_MERGE_PATCH`, and an empty/no-change patch creates no version or Audit change.
- Patch／archive／restore require strict `If-Match`: missing `428`, malformed `400`, stale `412`.
- Repeated archive or restore with the current ETag is an idempotent no-op: no version increment and no Audit event.
- Archived Campaign or association rejects ordinary patch with `409 RESOURCE_ARCHIVED`.
- Archived Campaign blocks all association mutation with `409 RESOURCE_ARCHIVED`; archived Product blocks it with `409 PRODUCT_ARCHIVED`.
- Reads remain available for archived Campaigns, Products, and associations.

## Transaction and Audit boundary

- Each command creates exactly one trusted `AuditOperationContext`; Browser input never selects the actor.
- Campaign Plan uses `entity_type=CAMPAIGN_PLAN` and nullable `product_uuid`.
- Association uses `entity_type=CAMPAIGN_PRODUCT`, `entity_uuid=campaignProductUuid`, and the associated `product_uuid`.
- Audit value types：budgets and `budget_weight` use `DECIMAL`; `priority` uses `INTEGER`; dates use `DATE`; lifecycle uses `ENUM`; text／URL／UUID use their approved types.
- CREATE／UPDATE／ARCHIVE／RESTORE record actor, request ID, actual fields, and continuous `change_order` only.
- Failed, stale, blocked, duplicate, validation, empty-patch, and idempotent operations leave no Audit.
- Domain mutation and Audit commit or roll back together.
- Cross-entity active-state checks and association uniqueness checks occur inside the same transaction as mutation and version validation. Concurrent duplicate association attempts must result in one success and one deterministic conflict, not a 500.

## Frontend and BFF

- `/campaigns` provides loading, empty, error, search, status filter, sort, pagination, archive, and restore states.
- `/campaigns/new` creates a Campaign and navigates to its detail.
- `/campaigns/[campaignUuid]` edits Campaign fields and manages Product associations, including Product lookup, add, edit metadata, archive, restore, 409／412／428 recovery, and archived-Campaign read-only messaging.
- Product Detail `?tab=campaigns` lists associations through the approved Campaign collection filter and supports add／edit／archive／restore while respecting archived Product and Campaign boundaries.
- Unknown Product Detail tabs continue to fall back to Product Master.
- Campaign BFF paths, methods, collection queries, request headers, response headers, timeout, and body size are separately allowlisted. Detail endpoints do not receive collection-only query parameters.
- BFF preserves Backend status/body plus `Content-Type`, `ETag`, `Location`, and `X-Request-ID`; it never forwards Cookie, Authorization, `X-Actor-ID`, hop-by-hop headers, or arbitrary targets.
